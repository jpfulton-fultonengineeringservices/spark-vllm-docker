# System Boundary Interface Documentation

This document describes the system's external invocation interfaces, including CLI commands, API endpoints, configuration parameters, and other boundary mechanisms.

## Command Line Interface (CLI)

### bash mods/instanttensor-zero-copy/run.sh

**Description**: Executable entry point of the InstantTensor zero-copy weight loader mod. It validates that python3 and the bundled patcher script are present and then runs patch_weight_utils.py to rewrite the installed vLLM weight-iterating code. The install location of vLLM can be overridden through the VLLM_PACKAGE_ROOT environment variable (primarily for tests or non-standard installs). Runs under 'set -euo pipefail' and prints prefixed log lines.

**Source File**: `.litho/tree/repo/mods/instanttensor-zero-copy/run.sh`

**Options**:

- `VLLM_PACKAGE_ROOT`(string (path)): optional - Absolute path to the installed vLLM package root that should be patched. When unset, the script resolves the active Python environment's site-packages automatically. Used by tests and non-standard installations. (default: `auto-detected site-packages root of the active Python environment`)

**Usage Examples**:

```bash
bash mods/instanttensor-zero-copy/run.sh
```

```bash
VLLM_PACKAGE_ROOT=/usr/local/lib/python3.12/dist-packages/vllm bash mods/instanttensor-zero-copy/run.sh
```

### bash mods/diffusiongemma/run.sh

**Description**: Main entry point of the DiffusionGemma mod. It resolves the Python site-packages root, applies diffusiongemma-support.patch, then tries the main-branch attention and sanitizer patches with legacy fallbacks, applies the streaming-reasoning and docs patches, and finally launches the vLLM server using chat_template_no_think.jinja. Uses 'set -euo pipefail' for fail-fast behaviour; the exit code is that of the launched server or of the first failing patch step.

**Source File**: `.litho/tree/repo/mods/diffusiongemma/run.sh`

**Usage Examples**:

```bash
bash mods/diffusiongemma/run.sh
```

### bash mods/fix-glm-4.7-flash-AWQ/run.sh

**Description**: Entry point of the GLM-4.7-Flash-AWQ fix mod. It applies glm47_flash.patch to the root filesystem to install the Triton MLA performance fix, then greps the installed vLLM mla_attention.py for the PR 34695 fix marker and only applies glm47_vllm_bug.patch when the crash fix is still missing, making the workflow idempotent. Runs with 'set -e' so any failure aborts the run.

**Source File**: `.litho/tree/repo/mods/fix-glm-4.7-flash-AWQ/run.sh`

**Usage Examples**:

```bash
bash mods/fix-glm-4.7-flash-AWQ/run.sh
```

### bash mods/fix-qwen3-coder-next/run.sh

**Description**: Orchestration entry point of the Qwen3-Coder-Next patch kit. It forward-applies fix_crash.diff (fixes the startup crash in vLLM's single-type KV cache manager) and reverse-applies fix_slowness.diff with 'patch -p1 -R' against /usr/local/lib/python3.12/dist-packages (reverting upstream PR #34279). Both patch steps tolerate inapplicability and print a skip message instead of failing.

**Source File**: `.litho/tree/repo/mods/fix-qwen3-coder-next/run.sh`

**Usage Examples**:

```bash
bash mods/fix-qwen3-coder-next/run.sh
```

### recipe runner <recipe.yaml>  (consumes recipes/ declarative YAML recipes)

**Description**: The recipes/ directory defines the primary user-facing configuration interface of the repository. Each YAML recipe declares the model, container image, required mods, build arguments, environment variables and default serving parameters that an orchestration/recipe-runner tool turns into a vLLM server launch (or a container build). The values documented below are the option surface referenced by the recipes; all 'defaults' entries are explicitly documented as CLI-overridable in the recipe headers.

**Source File**: `.litho/tree/repo/recipes/ (3x-spark-cluster, 4x-spark-cluster, 8x-spark-cluster)`

**Arguments**:

- `recipe` (string (file path or recipe name)): required - Path or identifier of the recipe YAML file to deploy (e.g. recipes/4x-spark-cluster/qwen3.5-397b-a17B-fp8.yaml). The recipe supplies the model ID, container image, mods list, env block and defaults used for the launch.

**Options**:

- `--download-model`(boolean flag): optional - Download the declared model weights before serving. Documented in recipes/deepseek-v4-flash.yaml. (default: `false`)
- `--no-ray`(boolean flag): optional - Launch the multi-node vLLM cluster without Ray. Required by the 397B/3-node Spark recipes so that the full context fits on two Sparks. (default: `false`)
- `--chat-template`(string (path to .jinja file)): optional - Path to a Jinja chat template passed to the inference server. Used to apply the corrected Qwen3.5/Qwen3.6 templates and the DiffusionGemma no-think template from the mods directory. (default: `model-embedded chat template`)
- `--port`(integer): optional - TCP port for the served OpenAI-compatible inference API. Declared in the 'defaults' block of essentially every recipe. (default: `8000`)
- `--host`(string (IP address)): optional - Bind address of the inference server. (default: `0.0.0.0`)
- `--tensor-parallel`(integer): optional - Tensor-parallel size. Set to 2 for dual-Spark recipes, 4 for the 4x Spark cluster recipes (MiniMax-M2.5, Nemotron-3-Ultra-550B NVFP4, Qwen3.5-397B) and 8 for the 8x Spark GLM-5.2 NVFP4 recipe. (default: `1 (per recipe: 2, 4 or 8 depending on cluster size)`)
- `--pipeline-parallel`(integer): optional - Pipeline-parallel size. The 3x Spark Qwen3.5-397B INT4-Autoround recipe uses PP=3 across the three nodes. (default: `1`)
- `--gpu-memory-utilization`(number (GB) or fraction): optional - GPU memory budget for the KV cache and weights. Several recipes stress that the value must be expressed in GB (not as a fraction) so that the full context fits on DGX Spark hardware. (default: `container/recipe specific`)
- `--exp-mxfp4`(build flag): optional - Container build argument that enables the experimental MXFP4 build used by openai/gpt-oss-120b on the vllm-node-mxfp4 image. (default: `disabled`)
- `--exp-b12x`(build flag): optional - Container build argument that enables the experimental B12X stack used by the vllm-node-b12x image (DeepSeek-V4-Flash-0731, Qwen3.8-Flash-Next, GLM-5.2-NVFP4 recipes). (default: `disabled`)

**Usage Examples**:

```bash
recipe-runner recipes/deepseek-v4-flash.yaml --download-model
```

```bash
recipe-runner recipes/3x-spark-cluster/qwen3.5-397b-int4-autoround.yaml --no-ray
```

```bash
recipe-runner recipes/4x-spark-cluster/minimax-m2.5.yaml --port 8000 --tensor-parallel 4
```

```bash
recipe-runner recipes/openai-gpt-oss-120b.yaml --exp-mxfp4
```

## API Interfaces

### Python (in-process function / torch.autograd.Function call) inkling_sm120_fa4.interface.flash_attn_func

**Description**: Public dense FlashAttention entry point of the vendored kernel package, supporting NVIDIA Hopper (SM90) and Blackwell (SM100/SM120) GPUs. The call validates shapes, dtypes, devices and head dimensions, parses the device architecture, computes tile sizes and split-KV heuristics, and dispatches into the CuTe-DSL kernels through the FlashAttnFunc autograd wrapper so that it can be used directly inside PyTorch autograd graphs.

**Source File**: `.litho/tree/repo/mods/inkling-sm12-paged-kv/vendor/inkling_sm120_fa4/interface.py`

**Request Format**: Tensors plus configuration scalars: q, k, v (torch.Tensor, fp16/bf16), optional cu_seqlens, seqused_k, alibi_slopes, softmax_scale, causal / local-window flags, dropout_p and return_attn_probs.

**Response Format**: torch.Tensor attention output (optionally accompanied by the log-sum-exp tensor and RNG state for backward).

### Python (in-process function / torch.autograd.Function call) inkling_sm120_fa4.interface.flash_attn_varlen_func

**Description**: Variable-length (packed/ragged batch) FlashAttention entry point exposed through the FlashAttnVarlenFunc autograd class. Used for prefill on concatenated sequences and for MLA-style attention paths; implementation reuses the architecture detection, head-dimension validation and tiling heuristics of the dense path.

**Source File**: `.litho/tree/repo/mods/inkling-sm12-paged-kv/vendor/inkling_sm120_fa4/interface.py`

**Request Format**: Packed tensors q, k, v, cu_seqlens_q, cu_seqlens_k (and optional max_seqlen_q/k, seqused_k, alibi_slopes, causal/local flags, softmax_scale, dropout_p).

**Response Format**: torch.Tensor attention output for the packed layout, optionally with auxiliary LSE/RNG tensors for backward.

### Python (torch.autograd.Function: forward / backward) inkling_sm120_fa4.interface.FlashAttnFunc / FlashAttnVarlenFunc (autograd classes)

**Description**: Autograd integration boundary between PyTorch and the custom CUDA/CuTe-DSL kernels. Both classes implement forward() and backward() so training and inference code can differentiate through the attention call; backward reuses make_fake_bwd_tensors and the backward tile-size heuristics.

**Source File**: `.litho/tree/repo/mods/inkling-sm12-paged-kv/vendor/inkling_sm120_fa4/interface.py`

**Request Format**: Same tensor arguments as the functional entry points, called through ctx.save_for_backward-compatible objects.

**Response Format**: Forward returns the attention output; backward returns gradients for q, k, v (and any other differentiable inputs).

### Python (in-process helper function) inkling_sm120_fa4.interface.num_splits_heuristic

**Description**: Small public scheduling helper that decides how many split-KV partitions to use given the number of query blocks, SMs and key blocks. Exposed for callers that build their own kernel launch configurations.

**Source File**: `.litho/tree/repo/mods/inkling-sm12-paged-kv/vendor/inkling_sm120_fa4/interface.py`

**Request Format**: total_mblocks (int), num_SMs (int), num_n_blocks (int), max_splits (int)

**Response Format**: int number of splits

## Integration Suggestions

### Declarative recipe configuration (YAML)

New model deployments are added by dropping a YAML recipe into recipes/ (or one of the 3x/4x/8x-spark-cluster sub-directories). The recipe is the declarative contract between the repository and the orchestrator: recipe_version, name, description, model (HuggingFace ID), container image, build_args, mods list, solo_only / cluster_only flags, env map, and a defaults map that is explicitly documented as CLI-overridable.

**Example Code**:

```
recipe_version: 1
name: Qwen3.5-397B-A17B-FP8 (TP=4)
description: Multi-modal FP8 serving, requires ROPE fix mod
model: Qwen/Qwen3.5-397B-A17B-FP8
container: vllm-node
mods:
  - mods/fix-qwen3.5-autoround
cluster_only: true
defaults:
  port: 8000
  host: 0.0.0.0
  tensor_parallel: 4
```

**Best Practices**:

- Always set recipe_version so the runner can evolve the schema safely.
- Declare every required mod in the mods list; recipes with no mods use an empty list.
- Express gpu_memory_utilization in GB, not as a percentage/fraction, on DGX Spark hardware.
- Record hardware caveats in comments (for example NVIDIA driver 580.x is required on GB10 because 590.x triggers a CUDAGraph deadlock).
- Use cluster_only / solo_only to prevent deploying a recipe in an unsupported topology.

### Chat template override for the inference server

Corrected Jinja chat templates (mods/fix-qwen3.5-chat-template/chat_template.jinja, mods/fix-qwen3.6-chat-template/chat_template.jinja, mods/diffusiongemma/chat_template_no_think.jinja) replace the model-embedded template. They are loaded by the inference server through --chat-template and control how messages, tool definitions and multimodal content are serialized. Templates expose a render_content macro and use jinja2 namespace counters plus raise_exception for validation.

**Example Code**:

```
vllm serve Qwen/Qwen3.5-397B-A17B-FP8 \
  --chat-template mods/fix-qwen3.5-chat-template/chat_template.jinja
```

**Best Practices**:

- Pass the template explicitly with --chat-template so an upstream template change cannot silently regress serving.
- Keep the template declarative; raise_exception is the only supported way to reject invalid content (for example images inside a system message).
- Diff-template changes against the checkpoint's original template and document the intentional deltas (the DiffusionGemma template intentionally omits the prefilled empty thought channel when thinking is disabled).

### Patch orchestration through mod entry scripts

Every mod is self-contained and is applied by executing its run.sh from the shell. The scripts mutate an already-installed vLLM package with GNU patch ('patch -p1') or with AST-based Python patchers, and they are designed to be idempotent: they grep for an upstream marker before applying a fix and skip gracefully (or reverse-apply with -R) when a change is no longer applicable.

**Example Code**:

```
set -euo pipefail
patch -p1 -d /usr/local/lib/python3.12/dist-packages < fix_crash.diff
patch -p1 -R -d /usr/local/lib/python3.12/dist-packages < fix_slowness.diff || echo 'skipped: already reverted'
```

**Best Practices**:

- Apply mods in a deterministic order and fail fast ('set -e' / 'set -euo pipefail').
- Prefer reverse-application over deleting hunks of upstream code so that re-running a mod after an upstream revert stays safe.
- Log patch status so an operator can tell which mods took effect.
- Store the intended vLLM version next to the patch so that context mismatches are detected early.

### vLLM runtime environment variables

The recipes and mods tune the patched vLLM behaviour through environment variables instead of code changes. Notable variables seen in the repository are VLLM_PACKAGE_ROOT (target vLLM install for mods/instanttensor-zero-copy), VLLM_FLASHINFER_ALLREDUCE_BACKEND=trtllm, VLLM_ALLOW_LONG_MAX_MODEL_LEN=1, VLLM_SPARSE_INDEXER_MAX_LOGITS_MB, VLLM_B12X_MLA_CKV_GATHER, VLLM_USE_AOT_COMPILE and CUTE_DSL_ARCH=sm_121a (DGX Spark target architecture).

**Example Code**:

```
env:
  VLLM_ALLOW_LONG_MAX_MODEL_LEN: "1"
  VLLM_B12X_MLA_CKV_GATHER: "1"
  CUTE_DSL_ARCH: sm_121a
  VLLM_USE_AOT_COMPILE: "1"
```

**Best Practices**:

- Keep the env map inside the recipe YAML so that a deployment is fully reproducible from one file.
- Set CUTE_DSL_ARCH explicitly when compiling CuTe-DSL kernels for a non-default architecture such as sm_121a.
- Only enable experimental flags (VLLM_USE_AOT_COMPILE, VLLM_B12X_MLA_CKV_GATHER) on the hardware they were validated for.

### OpenAI-compatible inference endpoint exposed by the launched server

After a recipe launches the patched vLLM server (defaults: port 8000, host 0.0.0.0), client applications interact with the deployment over the standard OpenAI-compatible HTTP surface (for example /v1/chat/completions and /v1/models). The chat templates provided by this repository are consumed by that endpoint, so applications calling it automatically receive the corrected prompt rendering. Authentication is not configured by this repository and must be supplied by the surrounding deployment (for example a reverse proxy or an --api-key equivalent on the server side).

**Example Code**:

```
curl http://<spark-node>:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model": "Qwen/Qwen3.5-397B-A17B-FP8", "messages": [{"role": "user", "content": "Hello"}]}'
```

**Best Practices**:

- Pin the client to the port and host declared in the recipe's defaults block instead of hard-coding them.
- Keep templates and clients in sync: a template change alters the model input and can change model outputs.
- Expose the endpoint only inside the cluster unless authentication is added at the proxy layer.

### Vendored FlashAttention kernel package

mods/inkling-sm12-paged-kv/vendor/inkling_sm120_fa4 is a self-contained CuTe-DSL/CUTLASS kernel package consumed by vLLM (paged-KV attention on SM120). Integration happens at import time: vLLM's attention backend dispatches into inkling_sm120_fa4.interface, which in turn requires torch, cuda.bindings.driver, cutlass and quack.compile_utils at runtime.

**Example Code**:

```
from inkling_sm120_fa4.interface import flash_attn_func, flash_attn_varlen_func
out = flash_attn_func(q, k, v, causal=True)
```

**Best Practices**:

- Keep the vendored package version-pinned and re-vendor rather than monkey-patching it at runtime.
- Validate the device architecture before dispatch; the package derives compute capability from _parse_arch_str and validates head dimensions per architecture.
- Import torch and the CUDA driver bindings lazily if the package is only needed for specific backends.
