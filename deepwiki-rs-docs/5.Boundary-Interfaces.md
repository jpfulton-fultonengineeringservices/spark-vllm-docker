# System Boundary Interface Documentation

This document describes the system's external invocation interfaces, including CLI commands, API endpoints, configuration parameters, and other boundary mechanisms.

## Command Line Interface (CLI)

### ./mods/diffusiongemma/run.sh

**Description**: Executes DiffusionGemma patch application and vLLM server launch with a custom chat template.

**Source File**: `.litho/tree/repo/mods/diffusiongemma/run.sh`

### ./mods/fes-weights/run.sh

**Description**: Verifies and reorganizes FES-staged model weights for offline vLLM resolution.

**Source File**: `.litho/tree/repo/mods/fes-weights/run.sh`

**Options**:

- `FES_WEIGHTS_DIR`(string): optional - Directory containing FES-staged model weights (default: `/model`)
- `FES_DRAFT_DIR`(string): optional - Optional directory for draft-model weights
- `FES_HUB_MODEL`(string): optional - HuggingFace model identifier; when set, triggers hub-cache layout creation

**Usage Examples**:

```bash
FES_WEIGHTS_DIR=/mnt/models FES_DRAFT_DIR=/mnt/draft ./mods/fes-weights/run.sh
```

### ./mods/fix-glm-4.7-flash-AWQ/run.sh

**Description**: Applies GLM 4.7 Flash Triton MLA performance patch and idempotent crash fix.

**Source File**: `.litho/tree/repo/mods/fix-glm-4.7-flash-AWQ/run.sh`

### ./mods/fix-qwen3-coder-next/run.sh

**Description**: Applies crash fix and reverts performance-regressing patch for Qwen3-Coder-Next.

**Source File**: `.litho/tree/repo/mods/fix-qwen3-coder-next/run.sh`

### ./mods/memory-profile/run.sh

**Description**: Installs memory profiling instrumentation and initiates profile collection.

**Source File**: `.litho/tree/repo/mods/memory-profile/run.sh`

### ./mods/instanttensor-zero-copy/run.sh

**Description**: Applies InstantTensor zero-copy weight loader patch for vLLM.

**Source File**: `.litho/tree/repo/mods/instanttensor-zero-copy/run.sh`

**Options**:

- `VLLM_PACKAGE_ROOT`(string): optional - Override vLLM installation root directory (used for testing or non-standard installs)

**Usage Examples**:

```bash
VLLM_PACKAGE_ROOT=/usr/local/lib/python3.12/dist-packages/vllm ./mods/instanttensor-zero-copy/run.sh
```

### ./docker/build_flashinfer_jit_providers.sh

**Description**: Builds FlashInfer JIT-cache provider wheels for specified CUDA architectures.

**Source File**: `.litho/tree/repo/docker/build_flashinfer_jit_providers.sh`

**Arguments**:

- `python` (string): required - Path to Python interpreter to use for building
- `wheel_dir` (string): required - Output directory for built wheel files

**Options**:

- `FLASHINFER_JIT_CACHE_PROVIDER_ARCHS`(string): required - CUDA architectures to target (e.g., '90a;100')

**Usage Examples**:

```bash
FLASHINFER_JIT_CACHE_PROVIDER_ARCHS='90a;100' ./docker/build_flashinfer_jit_providers.sh /usr/bin/python3 /tmp/wheels
```

## Integration Suggestions

### source_patch

Integrate mods into vLLM build process by applying run.sh scripts during Docker image build. Each mod applies patches to the installed vLLM package; the run.sh script orchestrates the patching.

**Example Code**:

```
RUN cd /opt/mods/fes-weights && bash run.sh
```

**Best Practices**:

- Apply mods in a specific order if they modify the same files; check for idempotency (e.g., fix-glm-4.7-flash-AWQ skips if already applied).
- Use environment variables like VLLM_PACKAGE_ROOT to target non-standard installations.
- Include the mod's run.sh in the build step after pip install vllm.

### configuration

Leverage deployment recipes (YAML files in recipes/) to configure vLLM serving parameters for specific model architectures and cluster sizes. These recipes are intended for use with an orchestrator (e.g., run-recipe.sh).

**Example Code**:

```
# Invoke orchestrator with recipe: run-recipe.sh recipes/4x-spark-cluster/qwen3.5-397b-int4-autoround.yaml
```

**Best Practices**:

- Use recipe defaults for port, host, tensor_parallel, and GPU memory utilization, but override via CLI when needed.
- Set cluster_only flag for recipes that require multi-node Spark clusters.
- Include required mods in the recipe's mods list to automatically apply needed patches.

### environment_variable

The fes-weights mod uses environment variables to configure weight directories. This allows flexible integration with different storage mounts or cluster setups.

**Example Code**:

```
export FES_WEIGHTS_DIR=/data/models && bash mods/fes-weights/run.sh
```

**Best Practices**:

- Set FES_WEIGHTS_DIR to the path where model weights are mounted.
- Use FES_DRAFT_DIR for models with separate draft weight directories.
- Set FES_HUB_MODEL to the HuggingFace model ID to automatically create a hub-cache structure for offline resolution.

### library_dependency

The inkling-sm12-paged-kv mod provides a custom FlashAttention implementation for SM120 GPUs. It is imported as a Python package and used with vLLM's attention backend.

**Example Code**:

```
from inkling_sm120_fa4.interface import FlashAttnFunc
```

**Best Practices**:

- Ensure torch and CUDA driver bindings are available.
- The module auto-detects GPU architecture; ensure compute capability >= 90 (Hopper) for full support.

### build_tool

The docker/build_flashinfer_jit_providers.sh script builds specialized FlashInfer JIT-cache provider wheels for the target CUDA architectures. This is needed when FlashInfer is used with custom kernels.

**Example Code**:

```
docker/build_flashinfer_jit_providers.sh /usr/bin/python3 /tmp/wheels
```

**Best Practices**:

- Run from a FlashInfer source checkout directory.
- Set FLASHINFER_JIT_CACHE_PROVIDER_ARCHS to match the target GPU compute capabilities.
- Use the built wheels in the Docker image to reduce JIT compilation at runtime.
