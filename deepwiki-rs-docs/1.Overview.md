## 1. Project Introduction

### 1.1 Project Name and Description

**Project Name:** `spark-vllm-docker`

**Description:** `spark-vllm-docker` is a patch-and-orchestration layer built around the open-source vLLM large language model (LLM) serving engine, purpose-built for Spark clusters equipped with NVIDIA Blackwell GPUs. The project does not reimplement a serving engine; instead, it supplies a curated set of source-level patches, custom attention kernels, memory profiling tooling, offline model weight preparation scripts, and declarative deployment recipes that together enable vLLM to run efficiently and correctly on SM90/SM100/SM120-class NVIDIA hardware in clustered, often network-constrained, environments.

The system is composed of seven primary domains:

| Domain | Role | Importance |
|---|---|---|
| Attention Kernel Domain | Custom FlashAttention kernels vendored for Blackwell GPUs | Core |
| Engine Patching & Model Compatibility Domain | Source patches, AST rewriters, and chat templates for vLLM/transformers | Core |
| Deployment Recipes & Cluster Orchestration Domain | YAML recipes and runners that bind mods and launch clusters | Core |
| Memory Profiling & Capacity Domain | Startup instrumentation and host capacity validation | Supporting |
| Model Weights & Offline Serving Domain | Weight verification and HF hub-cache layout | Supporting |
| Container Build & Image Composition Domain | Dockerfiles and build-time patch toolchain | Infrastructure |
| Developer Tooling Domain | Evaluation runners and documentation generators | Tool Support |

### 1.2 Core Functionality and Business Value

The core business value of `spark-vllm-docker` is to **enable efficient, correct, and reproducible deployment of large language models on Spark clusters with NVIDIA Blackwell GPUs** by providing:

1. **Hardware-specific optimizations** — vendored CuTe-DSL FlashAttention kernels (forward, backward, MLA, split-K, paged-KV) for SM90/SM100/SM120 architectures, integrated into vLLM through an AST-based dispatch patch.
2. **Model compatibility remediation** — targeted patches and corrected chat templates that restore quantization, serialization, and architecture support for Qwen3/Qwen3.5/Qwen3.6, Gemma4, DiffusionGemma, GLM-4.7, Nemotron, MiniMax, Step-3.7, Mimo, RadixArk, and others.
3. **Topology-aware capacity planning** — memory profiling instrumentation that records per-phase startup memory, consolidates results into profile cards, and validates that a deployment fits available host memory before cluster launch.
4. **Offline-first serving** — weight verification and Hugging Face hub-cache construction that allow fully air-gapped inference.
5. **Declarative, repeatable deployment** — YAML recipes for 3×, 4×, and 8× Spark cluster topologies that sequence modifications and launch head/worker nodes deterministically.

The system eliminates the need for ad-hoc, manual patching of vLLM at deployment time, reducing mean-time-to-deploy, preventing configuration drift between cluster nodes, and enabling support for emerging model architectures without waiting for upstream vLLM releases.

| Characteristic | Detail |
|---|---|

## 2. Target Users

### 2.1 User Role Definitions

The system serves two primary user personas:

#### 2.1.1 ML Infrastructure Engineer

**Description:** Engineers responsible for deploying and optimizing LLM inference on Spark clusters with NVIDIA Blackwell hardware. They are the primary operators of the system and the owners of recipe definitions and cluster launch procedures.

**Key needs:**
- Apply hardware-specific optimizations to vLLM for Blackwell GPUs.
- Resolve model compatibility issues with vLLM for Qwen3, Gemma, and other architectures.
- Profile and estimate memory capacity for cluster nodes prior to deployment.
- Verify weight integrity for offline model serving in network-constrained environments.
- Deploy vLLM across Spark cluster environments with custom chat templates and quantization configurations.

#### 2.1.2 AI Model Developer

**Description:** Researchers or engineers working on novel model architectures that require patching vLLM for support. They author new mods and recipes rather than simply consuming existing ones.

**Key needs:**
- Integrate custom quantization support (e.g., NVFP4) for MoE routers.
- Apply patches to support emerging model variants (e.g., DiffusionGemma, Qwen3.5).
- Leverage advanced attention kernels (MLA) for Blackwell hardware.

The following scenarios capture how each persona interacts with the system:

**Scope:** Optimizing the vLLM serving engine for Spark clusters with Blackwell GPUs through source-level patches, custom attention kernels, and deployment tooling.

The system boundary encompasses everything required to take a stock vLLM installation and transform it into a production-ready, hardware-optimized inference service on a Spark cluster — from image build, through modification sequencing, to cluster launch and post-launch capacity validation.

## 4. External System Interactions

### 4.1 External System List

| # | External System | Type | Interaction Description |
|---|---|---|---|
| 1 | **vLLM** | Software dependency | Open-source LLM serving engine that is patched and extended by this project. Consumed as a dependency, never forked. |
| 2 | **FlashInfer** | Software dependency | Library for high-performance attention kernels; used as a dependency in patching and JIT compilation. |
| 3 | **NVIDIA Blackwell GPU (SM120)** | Hardware platform | Target hardware platform for kernel customization and performance optimization. |
| 4 | **Hugging Face Hub** | External data source | Model repository used for offline weight access in cluster deployments. |

### 4.2 Interaction Method Descriptions

#### 4.2.1 vLLM — Source Patching and Extension

- **Interaction type:** Patches and extends source code.
- **Direction:** `spark-vllm-docker` → `vLLM` (outbound).
- **Mechanism:** Non-invasive, idempotent AST/text rewrites with mod markers applied to the installed vLLM Python package. Patches are applied at two points:
  - **Build time:** Shared patch library under `docker/` (e.g., `patch_vllm_flashinfer_b12x_swigluoai.py`, `patch_vllm_spark_kv_cache_cleanup.py`, `patch_vllm_startup_heap_trim.py`) executed during Docker image build.
  - **Runtime:** Per-model fix and feature mods under `mods/fix-*` and `mods/<feature>/` executed by `run-recipe` before server start.
- **Purpose:** Restore quantization behavior, fix chat templates, enable unsupported model architectures, inject attention kernel dispatch logic, and instrument startup memory profiling.
- **Contract:** The system targets specific vLLM versions; patches are validated for idempotency to allow safe re-application.

#### 4.2.2 FlashInfer — Kernel Source and JIT Compilation

- **Interaction type:** Provides kernel source and JIT compilation.
- **Direction:** `spark-vllm-docker` → `FlashInfer` (outbound) during image build.
- **Mechanism:**
  - FlashInfer is installed as a dependency in the Docker image.
  - `docker/build_flashinfer_jit_providers.sh` builds FlashInfer JIT-cache provider wheels for target CUDA architectures.
  - `docker/validate_flashinfer_wheels.py` validates built wheels and pins CUTLASS DSL versions for reproducibility.
  - FlashInfer sources are patched by `docker/patch_vllm_flashinfer_b12x_swigluoai.py` for SwiGLU-OAI parameter plumbing.
- **Purpose:** Provide high-performance attention kernels and JIT-compiled providers that complement the vendored FlashAttention package.

#### 4.2.3 NVIDIA Blackwell GPU (SM120) — Target Hardware Platform

- **Interaction type:** Target hardware platform.
- **Direction:** `spark-vllm-docker` → Hardware (outbound, via CUDA runtime).
- **Mechanism:**
  - Vendored CuTe-DSL FlashAttention kernels are compiled/loaded for SM90/SM100/SM120 compute capabilities.
  - The FA4 dispatch patch injects a `_use_sm12_paged_kv` capability check so that compute-capability 12.x devices route attention work to the vendored paged-KV kernel.
  - Memory profiling probes sample CUDA memory and native heap during worker startup to validate hardware capacity.
- **Purpose:** Deliver architecture-specific kernel selection (forward/MLA/split-K/TMA variants) and accurate capacity planning for Blackwell-class GPUs.

#### 4.2.4 Hugging Face Hub — Model Weight Source

- **Interaction type:** Model weight source.
- **Direction:** `spark-vllm-docker` → `Hugging Face Hub` (outbound, typically pre-deployment).
- **Mechanism:**
  - `hf-download.sh` provides a weight download helper for staging weights to local storage.
  - `mods/fes-weights/run.sh` constructs the HF hub-cache layout from staged weights for offline serving.
  - `mods/fes-weights/verify.py` validates staged shards against safetensors index, checks total size parity, and enforces quantization config presence for NVFP4 checkpoints.
- **Purpose:** Enable fully offline, air-gapped inference by resolving model weights from local storage rather than querying the Hugging Face hub at runtime.

### 5.3 Architecture Decision Descriptions

| # | Decision | Rationale | Trade-off |
|---|---|---|---|
| AD-1 | **Patch vLLM rather than fork it** | Avoids maintaining a divergent fork; enables easy upstream version upgrades. | Patches are coupled to vLLM source structure and may break across upstream releases. |
| AD-2 | **Idempotent AST/text rewrites with mod markers** | Allows safe re-application of patches and clear traceability of which mod applied which change. | AST patches are more complex to author and debug than simple file replacements. |
| AD-3 | **Split patching into build-time (`docker/`) and runtime (`mods/`)** | Build-time patches stabilize the image; runtime mods allow per-recipe flexibility without rebuilding. | Conceptually a single "Engine Compatibility" concern is physically split by execution timing, increasing cognitive load. |
| AD-4 | **Declarative YAML recipes as the composition root** | Recipes bind mods, weights, kernels, and cluster launch into a single reproducible artifact; users select a recipe rather than orchestrating steps manually. | Recipe catalog must be curated and kept in sync with available mods. |
| AD-5 | **Vendored FlashAttention package inside `mods/`** | Kernels are tightly coupled to this project's dispatch patch and target hardware; vendoring guarantees version stability. | Divergence from upstream FlashAttention; requires manual updates. |
| AD-6 | **Offline-first weight resolution via HF hub-cache construction** | Supports air-gapped Spark clusters; removes runtime dependency on Hugging Face hub availability. | Requires pre-staging of weights; weight verification becomes a hard prerequisite. |
| AD-7 | **Memory profiling as a supporting mod rather than a core engine feature** | Keeps instrumentation optional and out of the production hot path when not needed. | Profile cards must be regenerated when models or recipes change. |

## 6. Technical Architecture Overview

### 6.1 Main Technology Stack

| Layer | Technology | Usage |
|---|---|---|
| **Serving Engine** | vLLM (open-source) | Core LLM inference engine, patched and extended |
| **Attention Kernels** | CuTe-DSL (CUTLASS DSL), FlashAttention | Vendored SM90/SM100/SM120 forward/backward/MLA/split-K/paged-KV kernels |
| **Kernel Library** | FlashInfer | JIT-compiled attention provider wheels |
| **Deep Learning Framework** | PyTorch | Autograd interface for custom kernels; tensor operations |
| **GPU Compute** | NVIDIA CUDA (SM90, SM100, SM120) | Target hardware compute capability |
| **Model Format** | Safetensors, `hf_quant_config.json` | Offline weight storage and quantization metadata |
| **Templating** | Jinja2 (`.jinja` chat templates) | Model-specific chat serialization |
| **Packaging** | Docker (`Dockerfile`, `Dockerfile.mxfp4`) | Reproducible container images (base and MXFP4 variants) |
| **Configuration** | YAML (recipe files) | Declarative deployment specifications |
| **Orchestration** | Bash (shell runners), Python | Recipe parsing, mod sequencing, cluster launch |
| **Instrumentation** | Python JSONL event logging | Per-phase memory profiling during vLLM startup |
| **Quantization** | NVFP4, MXFP4, AWQ, FP8, INT4 (AutoRound), W4A16 | Model compression schemes supported across recipes |

### 6.2 Architecture Patterns

| Pattern | Application in `spark-vllm-docker` |
|---|---|
| **Patch/Extension (non-invasive)** | vLLM is extended via idempotent AST/text patches rather than forked or subclassed. Mod markers provide traceability. |
| **Composition Root** | `run-recipe` serves as the composition root, binding mods, weights, kernels, and cluster launch into a single orchestrated flow. |
| **Declarative Configuration** | YAML recipes describe desired end state (model, quantization, parallelism, cluster size, mods); the runner derives imperative steps. |
| **Strategy/Modularity** | Each mod under `mods/` is an independent, composable unit with a `run.sh` entry point; recipes select which strategies to activate. |
| **Vendoring** | The FlashAttention kernel package is vendored to decouple from upstream release cadence. |
| **Build-Time vs. Runtime Layering** | Image-stable patches applied at build time (`docker/`); recipe-specific patches applied at runtime (`mods/`). |
| **Instrumentation/Observer** | The memory profiling probe observes vLLM worker startup without altering serving behavior. |
| **Fail-Fast Validation** | Weight verification and capacity checks fail before deployment if preconditions are not met. |
