## 1. Architecture Overview

### 1.1 Architecture Design Philosophy

`spark-vllm-docker` is not an inference engine of its own. It is a **patch-and-orchestration layer** wrapped around the open-source **vLLM** serving engine, purpose-built for Spark clusters equipped with NVIDIA Blackwell GPUs (compute capability SM12.x, plus SM90/SM100 fallback coverage).

The architecture is governed by four design convictions:

1. **Patch, never fork.** All behavioural changes to vLLM are applied as *non-invasive, idempotent source rewrites* against the installed package. The upstream dependency is never vendored as a fork, never modified in version control, and never diverged in a way that blocks rebasing. Marker comments (`# spark-vllm mod: …`) make every edit traceable and double-application detectable.
2. **Fail fast, never guess.** Patching scripts resolve an exact anchor, require exactly one occurrence, validate the target source with `ast.parse`, compile the rewritten output, and *abort* on any unknown source shape. Corrupting a build or a serving container is treated as strictly worse than refusing to start.
3. **Declarative composition root.** The single user-facing artifact is a **YAML recipe**. Recipes bind a model, its quantization scheme, its required mods, environment variables, and a `vllm serve` command template into one reproducible unit. Everything else — image build, weight verification, kernel dispatch, cluster launch — is orchestrated *from* the recipe.
4. **Offline-first serving.** Spark clusters are frequently air-gapped or network-constrained. Weight staging, integrity verification, and Hugging Face hub-cache layout are first-class architectural concerns, not afterthoughts.

### 1.2 Core Architecture Patterns

| Pattern | Realization in this system |
|---|---|
| **Patch-and-extend an external dependency** | Idempotent AST/text rewrites of the installed `vllm`/`flashinfer`/`b12x` trees, applied at build time (`docker/patch_*.py`) and at run time (`mods/*/run.sh`). |
| **Composition root** | Recipe YAML + `run-recipe.py`, which sequences *Load Recipe → Resolve Nodes → Build → Download → Run*. |
| **Plugin / mod protocol** | Every directory under `mods/` implements an implicit contract: `run.sh` entry point, target discovery via `importlib.util.find_spec("vllm")`, marker-guarded idempotency, fail-fast policy, composition via `launch-cluster.sh --apply-mod`. |
| **Two-tier patch lifecycle** | Build-time patches are baked into the image layer; runtime mods are applied container-locally just before `vllm serve`. Both tiers target the *same* installed tree. |
| **Vendoring into third-party namespace** | The CuTe-DSL FlashAttention package is copied into `vllm/third_party/inkling_sm120_fa4` and wired in through an AST dispatch patch. |
| **Instrumentation-as-mod** | The memory profiler installs itself *into* vLLM as `vllm._spark_memory_profile`, observing engine startup from the inside. |
| **Declarative infrastructure** | Dockerfiles, recipe YAMLs, `build-metadata.yaml`, and profile cards express intent; scripts merely execute it. |
| **Fail-fast validation gates** | Weight verification (shard/index/size/quant-config) and build-time patch validation both abort on mismatch. |

### 1.3 Technology Stack Overview

| Layer | Technology |
|---|---|
| Serving engine | vLLM (upstream, unmodified in VCS; installed into dist-packages) |
| Attention/kernels | FlashInfer, B12X, vendored CuTe-DSL FlashAttention (`inkling_sm120_fa4`), CUTLASS DSL 4.7.0 |
| GPU platform | NVIDIA Blackwell SM120/SM121 (SM80/SM90/SM100 kernels retained as fallbacks), CUDA 12.8+ / CUDA 13.0.2 base image |
| Deep learning runtime | PyTorch 2.13, NCCL (sm_121 build) |
| Container | Docker multi-stage builds; `Dockerfile` (901 lines) and `Dockerfile.mxfp4` variant; `build-and-copy.sh` (1,505 lines) |
| Orchestration | Bash + Python: `run-recipe.sh` (42-line wrapper) → `run-recipe.py` (1,546 lines) → `launch-cluster.sh` (1,751 lines), `autodiscover.sh`, `hf-download.sh` |
| Configuration | YAML recipes (42 files across `recipes/`, `recipes/3x|4x|8x-spark-cluster/`), `.env`, shell environment |

| Serving interface | OpenAI-compatible HTTP endpoint on port 8000 (Ray or no-Ray distributed mode) |

## 2. System Context (C4 — Level 1)

### 2.1 System Positioning and Business Value

The system enables efficient deployment of large language models on Spark clusters with NVIDIA Blackwell GPUs by supplying hardware-specific kernel optimizations, memory capacity analysis, and targeted model-compatibility fixes for architectures such as Qwen3/Qwen3.5/Qwen3.6, Gemma4, DiffusionGemma, GLM-4.7, Nemotron, MiniMax, Step-3.7, Mimo, and RadixArk.

Its value proposition is the **compression of an otherwise manual, error-prone integration path**: without this layer, an operator would have to hand-patch vLLM for every emerging model, guess host memory sizing for multi-billion-parameter checkpoints, and reconstruct offline weight layouts per cluster.

### 2.2 User Roles and Scenarios

| Persona | Profile | Primary scenarios |
|---|---|---|
| **ML Infrastructure Engineer** | Owns LLM inference deployment and tuning on Spark/Blackwell | Apply hardware-specific optimizations; fix model compatibility issues; profile and estimate node memory capacity; verify weight integrity for offline serving; deploy vLLM with custom chat templates across 3x/4x/8x clusters. |
| **AI Model Developer** | Works on novel architectures and quantization schemes | Integrate custom quantization (e.g. NVFP4 for MoE routers); add patches for emerging variants (DiffusionGemma, Qwen3.5); leverage advanced attention kernels (MLA, split-K) on Blackwell. |

### 2.4 System Boundary Definition

**Included in scope**
- Docker image definitions and build-time patch library (`Dockerfile`, `Dockerfile.mxfp4`, `docker/`)
- 29 runtime mods under `mods/` (fix mods, feature mods, kernel mod, profiling mod, weight mod, flavor mods)
- 42 recipe YAMLs covering solo and 3x/4x/8x cluster deployments
- Vendored SM120 FlashAttention kernel package
- Memory profiling, profile-card generation, and capacity validation
- Weight verification and offline hub-cache construction
- Cluster launch scripts (container-level bootstrap and node distribution)
- Developer tooling (evaluation runner, DeepWiki documentation generator)

**Excluded from scope**
- Core vLLM development
- Model training pipelines
- Hardware design and device drivers
- Spark cluster fleet management and provisioning (only *container-level* orchestration is performed; `launch-cluster.sh` and `autodiscover.sh` are a thin node-bootstrap layer, consistent with this boundary)

### 3.4 Storage Design

There is no database. All state is **file-based, locally persisted, and reproducible from artifacts on disk**:

| Store | Location | Content | Producer → Consumer |
|---|---|---|---|
| Recipe catalog | `recipes/**/*.yaml` | Model, quantization, mods, defaults, env, command template, build args, cluster/solo flags | Author → `run-recipe.py` |
| Mod implementations | `mods/<name>/` | `run.sh`, `patch_*.py`, `.patch`/`.diff`, Jinja templates, vendored kernels | Author → `launch-cluster.sh --apply-mod` |
| Build-time patch library | `docker/patch_*.py` | 21 idempotent rewriters executed inside the image build | Dockerfile → installed package |
| Container images | Docker daemon / worker hosts | Base or MXFP4 variant with patches and vendored kernels baked in | `build-and-copy.sh` → `launch-cluster.sh` |
| Wheel cache / releases | `wheels/` (empty) + GitHub Releases | FlashInfer JIT provider wheels, prebuilt vLLM wheels, arch `12.1a` | `build_flashinfer_jit_providers.sh` → image build |
| Build metadata | `build-metadata.yaml` | Reproducibility record for a given image build | `build-and-copy.sh` → operators |
| Model weights | `FES_WEIGHTS_DIR` mount | safetensors shards, index, `hf_quant_config.json` | Staging → `mods/fes-weights` → vLLM |
| Offline hub-cache | HF cache layout under mount | Resolvable local model tree for air-gapped serving | `mods/fes-weights/run.sh` → vLLM runtime |
| Memory events | per-run directories, JSONL | Per-rank, per-phase heap/CUDA/model/KV samples | `probe.py` → `collect.py` |
| Profile cards | model/recipe-keyed YAML | Merged phase peaks, startup RAM estimate, KV budget | `profile_card.py` → `capacity.py` → `launch-cluster.sh` |
| Capacity report | generated report file | Human-readable topology validation metrics | `report.py` + `host_probe.py` → operator |

### 3.5 Inter-Container Communication

Communication is almost entirely **process invocation and file exchange** — there are no networked internal services.

| Mechanism | From → To | Description |
|---|---|---|
| Phase delegation | Recipe runner → Build / Download / Launch | `run-recipe.py` shells out to `build-and-copy.sh`, `hf-download.sh`, `launch-cluster.sh`; supports phase-only flags (`--build-only`, etc.). |
| Ordered mod invocation | Launcher → any mod | `launch-cluster.sh --apply-mod <dir>` (repeatable, order-preserving); the `mods: []` list in the recipe is the source of ordering. |
| Target discovery contract | Mod → installed package | `importlib.util.find_spec("vllm")`, overridable via `VLLM_PACKAGE_ROOT` / `VLLM_SITE_PACKAGES`. |
| Configuration dependency | Recipe → Mod | Recipe declares mods, environment, and command template; mods are otherwise ignorant of the recipe. |
| Data dependency | Weights mod → vLLM | Verified hub-cache layout consumed at serve time. |
| Instrumentation dependency | Profiling mod → vLLM | Plugin installed as `vllm._spark_memory_profile` with manifest `vllm/_spark_memory_profile.json`. |
| Feedback loop | Capacity report → Launcher | Profile cards guide topology-appropriate host selection on the next launch. |
| Topology discovery | Launcher → `autodiscover.sh` / `.env` | Head/worker node resolution for cluster recipes. |

### 4.2 Technical Support Components

#### 4.2.1 Memory Profiling & Capacity

| Component | File | Responsibility |
|---|---|---|
| Startup Memory Probe | `probe.py` | Runs as `vllm._spark_memory_profile`; records per-phase native heap, CUDA memory, and model/KV inventory during worker startup; also usable as a standalone sampler. |
| Probe Installer | `patch.py` + `run.sh` | Installs the plugin into the vLLM package and emits manifest `vllm/_spark_memory_profile.json`. |
| Profile Collection | `collect.py` | Per-rank JSONL summarization from run directories. |
| Card Generation | `profile_card.py` | Merges events into a consolidated model/recipe-keyed YAML profile card; computes phase peaks. |
| Capacity Analysis | `capacity.py` | Estimates startup RAM, budgets KV cache, validates against available host memory per topology. |
| Reporting | `report.py`, `host_probe.py` | Probes host hardware; emits human-readable capacity report and utilization metrics. |

#### 4.2.2 Model Weights & Offline Serving

- **Weight Verification** (`mods/fes-weights/verify.py`): shard/index consistency, size parity with 1.02 tolerance, mandatory `hf_quant_config.json` for NVFP4 checkpoints; fail-fast on mismatch.
- **Offline Hub Cache Setup** (`mods/fes-weights/run.sh`): `FES_WEIGHTS_DIR` defaulting and HF hub-cache layout construction so vLLM resolves models locally.
- **Download Helper** (`hf-download.sh`): online acquisition path for networked environments.

#### 4.2.3 Container Build & Image Composition

### 5.7 Exception Handling Mechanisms

| Failure class | Detection | Handling |
|---|---|---|
| **Unknown upstream source shape** | Exact-anchor `replace_once` finds ≠ 1 occurrence, or `ast.parse` fails | Hard abort with reason; never best-effort rewrite |
| **Double application** | Marker comment `# spark-vllm mod: …` already present | Skip (idempotent no-op) |
| **Corrupted rewrite output** | Compile check before write | Abort; original file left untouched |
| **Weight integrity failure** | Shard/index mismatch, size parity beyond 1.02 tolerance, missing `hf_quant_config.json` | Fail fast; recipe execution halts before launch |
| **Wheel validation failure** | `validate_flashinfer_wheels.py` | Build aborts; no final image layer committed |
| **Kernel preflight failure** | Non-SM12.x device, CUDA < 12.8, missing CUTLASS DSL API | Mod exits before any dispatch patch is written |
| **Host memory shortfall** | `capacity.py` topology validation | Deployment blocked; alternative host topology selected |
| **Rollback** | *Not formally implemented* | Idempotent patching mitigates blast radius, but no formal revert path exists (documented gap) |

## 6. Technical Implementation

### 6.1 Code View — The Mod Protocol (system-wide contract)

Every mod under `mods/<name>/` implements the same implicit interface, verified across `fix-qwen3-next-autoround`, `inkling-sm12-paged-kv`, `memory-profile`, `fes-weights`, and `fix-qwen3.5-chat-template`:

| Contract element | Implementation |
|---|---|
| Entry point | `run.sh` (bash with `set -euo pipefail`) |
| Target discovery | `importlib.util.find_spec("vllm")`; overridable via `VLLM_PACKAGE_ROOT` / `VLLM_SITE_PACKAGES` |
| Patch mechanism | Python rewriter (`patch_*.py`) with exact-anchor `replace_once`, `ast.parse` validation, compile-before-write |
| Idempotency | Marker comments (`# spark-vllm mod: <name> v<N>`) and "already patched → skip" checks |
| Failure policy | **Fail fast on unknown source shapes** |
| Composition | `launch-cluster.sh --apply-mod <dir>` (repeatable, order-preserving); declared in the recipe's `mods: []` |
| Assets | `.patch`/`.diff` files, Jinja chat templates, vendored kernel packages |

**Exemplar — `patch_inkling.py`:** validates target shape via `ast.parse`, refuses any source where the anchor does not appear exactly once, is idempotent via marker `# spark-vllm mod: inkling-sm12-paged-kv v1`, and compiles the patched output before writing. This is the reference implementation of the protocol's safety guarantees.

### 6.2 Two-Tier Patch Lifecycle (and the third channel)

```
BUILD TIME                                      RUNTIME
docker/patch_*.py  --->  image layer  --->      mods/*/run.sh  --->  container-local edits
(21 scripts run by Dockerfile)                  (invoked by launch-cluster.sh --apply-mod)

THIRD CHANNEL (undocumented in research):
launch-cluster.sh --apply-vllm-pr <PR#|URL>  --->  fetch PR, diff against origin/main,
                                                   apply to installed package with
                                                   SHA256-slugged label
```

Both of the first two tiers mutate the **same installed vLLM tree**, with no cross-tier dependency declaration. `run-recipe.py` mirrors the third channel through `runtime_vllm_pr_reference()` validation. Build-time builds emit `build-metadata.yaml`; runtime has **no equivalent record** of applied PRs.

### 6.3 Key Algorithm Design

**1. Anchor-based source rewriting with AST verification**
```
resolve target file (find_spec)
  → check marker present? skip (idempotent)
  → locate anchor text (must occur exactly once)
  → ast.parse(original)  → ast.parse(candidate)
  → compile(candidate)
  → atomic write
  → on any failure: abort with diagnostic
```

**2. Capability-gated kernel dispatch**
A cached predicate `_use_sm12_paged_kv()` inspects `torch.cuda.get_device_capability()`; when `capability.major == 12`, vLLM's FA4 dispatch routes to `inkling_sm120_fa4_adapter.flash_attn_varlen_func` instead of the stock kernel.

**3. Tile scheduling and split-K heuristics (`interface.py`, `tile_scheduler.py`)**
- Parses `FwdConfig`/`BwdConfig`, validates head dimensions, resolves causal/local-window parameters.
- Computes tile sizes and split-KV decisions; schedules persistent work tiles using CLC-based scheduling modes.
- When work is split across KV chunks, a combine kernel (`FlashAttentionForwardReduce`) merges partial results.
- Kernels are exposed through PyTorch autograd Functions: `FlashAttnFunc`, `FlashAttnVarlenFunc`.

**4. Weight verification (`verify.py`)**
- Cross-checks every shard referenced by `model.safetensors.index.json` exists and is non-empty.
- Compares summed shard sizes against index-declared total within a 1.02 tolerance.
- Enforces presence and parseability of `hf_quant_config.json` for NVFP4 checkpoints.
- Any violation aborts the recipe before launch.

**5. Capacity estimation (`capacity.py`)**
- Sums per-phase peak host memory from the profile card (startup RAM) and adds a KV-cache budget derived from model/parallelism configuration.
- Validates the total against probed available host memory for each candidate topology.
- Emits utilization metrics consumed by host selection in `launch-cluster.sh`.

### 6.4 Data Structure Design

**Recipe YAML schema (validated fields)**

```yaml
name: qwen3.5-397b-int4-autoround
recipe_version: <int>
container: <image flavour selector>
command: <vllm serve command template>
mods:
  - fix-qwen3.5-chat-template
  - fix-qwen3-next-autoround
  - fes-weights
  - inkling-sm12-paged-kv
defaults:
  <parallelism and serving defaults>
env:
  <environment variables>
build_args:
  <arguments forwarded to build-and-copy.sh / Dockerfile selection>
cluster_only: true        # or solo_only: true
```

**Profile card (YAML)** — keyed by model/recipe; contains per-phase peak host memory, CUDA memory, model/KV inventory, and derived startup-RAM and KV-budget figures.

**Memory event (JSONL, one line per sample)** — rank, phase identifier, native heap bytes, CUDA bytes, model/KV inventory snapshot.

**Mod marker (source comment)** — `# spark-vllm mod: <mod-name> v<version>`; the sole idempotency and traceability token in patched sources.

**`build-metadata.yaml`** — record of image build inputs (patch set, PR ranges, wheel versions) emitted by `build-and-copy.sh`.

### 6.5 Performance Optimization Strategies

| Strategy | Mechanism |
|---|---|
| **Blackwell-native attention** | CuTe-DSL kernels specialized for SM120, including TMA-accelerated variants (`flash_fwd_sm120_tma.py`), MLA kernels, and split-K combine — reducing wasted compute on large-KV workloads. |
| **Paged-KV cache layout** | `paged_kv.py` prepares cache layouts for direct kernel consumption, avoiding layout conversion at dispatch time. |
| **Persistent tile scheduling** | CLC-based scheduling keeps SMs occupied across the whole launch rather than per-wave re-dispatch. |
| **Cooperative top-k / MoE tuning** | `patch_vllm_sm120_cooperative_topk.py`, `patch_vllm_b12x_moe_tuning_memory.py`, routed-experts weight-shape fixes reduce MoE routing overhead and memory pressure. |
| **Memory trims** | Startup heap trim, Spark KV-cache cleanup, and prealloc-cleanup mods reclaim host/CUDA memory before serving, directly increasing usable KV budget. |
| **Zero-copy weight loading** | `instanttensor-zero-copy` rewrites the weight iterator to use tensor views, eliminating redundant host-device copies. |
| **JIT wheel caching** | FlashInfer JIT provider wheels are built once, validated, and cached (`wheels/` + GitHub Releases) so subsequent image builds skip compilation. |
| **Speculative/hybrid decoding support** | Hybrid draft loader and MRv2 speculator cudagraph-pool patches enable draft-based latency reduction where models support it. |
| **Offline serving** | Hub-cache layout removes network round-trips at startup — a latency *and* availability optimization for air-gapped clusters. |

### 6.6 Security and Safety Design

- **Build integrity:** fail-fast patch validation prevents silently corrupted images; wheel validation and CUTLASS DSL pinning give reproducible builds.
- **Data integrity:** weight verification gates serving on cryptographic-file-layout consistency (index ↔ shards ↔ quant config).
- **Change traceability:** mod markers make every source mutation auditable in the running image.
- **Isolation:** all modifications occur inside the container filesystem; the host is untouched except for image distribution.
- **Known weaknesses:** runtime `--apply-vllm-pr` bypasses marker/idempotency conventions and is not recorded (gap G5); no formal rollback path for failed runtime mods (documented in §5.7).

### 7.4 Monitoring and Operations

**What exists today**
- Per-rank JSONL memory events and merged YAML profile cards (`mods/memory-profile`).
- Human-readable capacity reports with host-topology validation metrics.
- `build-metadata.yaml` for build-time reproducibility (patch set, PR ranges, wheel versions).
- Fail-fast diagnostics from every patcher, verifier, and preflight check.
- Automated documentation shadow tree via `scripts/deepwiki/`.

**Operational guidance**
1. **Always profile before a new cluster launch.** Run `mods/memory-profile/run.sh`, inspect the capacity report, and select hosts that pass topology validation — this is the cheapest way to avoid out-of-memory launches.
2. **Verify weights before serving.** Let `mods/fes-weights` gate the recipe; treat any verification failure as blocking.
3. **Preserve mod ordering.** The `mods: []` list in the recipe is the contract; ordering can matter (e.g. weight setup before serve, kernel dispatch before engine start).
4. **Treat upstream vLLM upgrades as a full revalidation event.** Anchor stability is the system's primary risk; re-run all patches and confirm no `replace_once` failures.
5. **Record runtime PR grafts manually** until `--apply-vllm-pr` writes an equivalent of `build-metadata.yaml`.
6. **Prefer build-time patches for anything reusable.** Reserve runtime mods for model/recipe-specific variation to minimize container-start variance.

**Recommended monitoring additions (gap-driven)**
- Emit a runtime manifest listing applied mods and PRs per container start (parity with `build-metadata.yaml`).
- Add a formal revert path for failed runtime mod application.
- Surface patch-anchor failures as an early CI signal against upstream vLLM `main`.
